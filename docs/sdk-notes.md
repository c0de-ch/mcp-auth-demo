# SDK notes — `@modelcontextprotocol/sdk` 1.30.0 authentication facts

Everything on this page was established by reading the **installed** SDK sources
(`node_modules/@modelcontextprotocol/sdk/dist/esm/**`) and by running the examples against them;
it is the list of things that silently break an MCP auth implementation when you get them wrong.
The per-example docs pages link here instead of repeating the details.

Protocol versions: the client sends `protocolVersion: 2025-11-25` in `initialize`; the server
supports `2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`, `2024-10-07` and rejects any
`mcp-protocol-version` header outside that list with 400. The authorization behaviour implemented
by the SDK is the MCP authorization specification of 2025-06-18 → 2025-11-25: Protected Resource
Metadata (RFC 9728), authorization-server metadata (RFC 8414) with OpenID Connect discovery
fallback, Dynamic Client Registration (RFC 7591), PKCE S256 (RFC 7636), resource indicators
(RFC 8707), token revocation (RFC 7009), `WWW-Authenticate` with `resource_metadata`, SEP-835 scope
selection and — client side only — Client ID Metadata Documents (SEP-991).

Not implemented by the SDK and therefore hand-rolled in the examples: the `client_credentials`
grant on the embedded authorization server, HTTP Basic client authentication at `/token`, a token
introspection server, RFC 8693 token exchange, DPoP, mutual TLS.

## Imports

Always import subpaths ending in `.js`, e.g. `@modelcontextprotocol/sdk/server/mcp.js`,
`…/server/streamableHttp.js`, `…/server/auth/router.js`, `…/server/auth/middleware/bearerAuth.js`,
`…/server/auth/errors.js`, `…/server/auth/providers/proxyProvider.js`, `…/client/index.js`,
`…/client/streamableHttp.js`, `…/client/auth.js`, `…/client/auth-extensions.js`, `…/shared/auth.js`,
`…/types.js`. The package's root export (`import … from '@modelcontextprotocol/sdk'`) does not
resolve in this build.

## Server side

- Imports: always use subpath imports ending in .js (e.g. '@modelcontextprotocol/sdk/server/mcp.js', '@modelcontextprotocol/sdk/server/auth/router.js'); the package 'exports' map is './*' -> dist/esm/*.js. The bare root export '.' points at dist/esm/index.js which does NOT exist in 1.30.0, so `import ... from '@modelcontextprotocol/sdk'` fails. './server' and './client' (no .js) also resolve to server/index.js and client/index.js.
- Express: the SDK declares express ^5.2.1 as a real dependency (deduped with the app's express 5.2.1; no nested copy). All routers/middleware are Express 5 (path-to-regexp v8: string wildcards like '*' are invalid, use '/{*splat}'; req.query is a read-only getter; rejected promises from async handlers are forwarded to error middleware automatically; express.urlencoded defaults to extended:false). @types/express@5 is installed; the `req.auth` augmentation lives in bearerAuth.d.ts and is only visible in files that import that module.
- LAN testing: createMcpExpressApp() defaults to host '127.0.0.1' and installs localhostHostValidation(), so requests from 192.168.x.x machines (Host: 192.168.78.10:3000) get 403 {code:-32000,'Invalid Host: ...'}. Use createMcpExpressApp({ host: '0.0.0.0', allowedHosts: ['192.168.78.10','mcp.lan','localhost'] }) (hostnames only, no ports; IPv6 as '[::1]') or plain express() + express.json(). The deprecated transport options allowedHosts/allowedOrigins only act when enableDnsRebindingProtection:true and compare the FULL Host header (host:port) exactly.
- Body parsing: if express.json() (or createMcpExpressApp) is in front of /mcp you MUST call transport.handleRequest(req, res, req.body); without parsedBody the transport re-reads the already-consumed stream and returns 400 'Parse error: Invalid JSON'. Without any body parser call handleRequest(req, res) and the transport parses. The auth routers parse their own bodies (urlencoded for /authorize,/token,/revoke; json for /register).
- Issuer HTTPS check: createOAuthMetadata, mcpAuthRouter and mcpAuthMetadataRouter throw 'Issuer URL must be HTTPS' unless hostname is localhost/127.0.0.1 or env MCP_DANGEROUSLY_ALLOW_INSECURE_ISSUER_URL=true|1. The env var is read ONCE when router.js is first evaluated, so set it in the shell/.env (with `import 'dotenv/config'` as the very first import) — assigning process.env after the static imports is too late. For this project (http://192.168.x.x issuer) it is required. Fragments/query strings in the issuer also throw.
- requireBearerAuth error mapping: only InvalidTokenError -> 401 and InsufficientScopeError -> 403 carry WWW-Authenticate; any plain Error thrown by verifyAccessToken becomes 500 {error:'server_error'} with no header, which breaks client discovery on expired/invalid tokens. Always throw InvalidTokenError (from server/auth/errors.js) for bad tokens. A missing/malformed Authorization header is already a 401 invalid_token.
- AuthInfo.expiresAt is effectively mandatory: requireBearerAuth returns 401 'Token has no expiration time' if it is not a finite number, and 401 'Token has expired' if < Date.now()/1000. It is in SECONDS (JWT exp), not milliseconds. For API keys/static tokens set a far-future value.
- requireBearerAuth does NOT check audience/resource or issuer — do it in the verifier (jose jwtVerify issuer option + checkResourceAllowed on aud). AuthInfo.resource is informational only.
- Authorization header parsing is `header.split(' ')`: scheme is case-insensitive but exactly one space is expected; extra whitespace yields 401.
- PRM path: mcpAuthMetadataRouter serves /.well-known/oauth-protected-resource + pathname of resourceServerUrl (for https://h/mcp -> /.well-known/oauth-protected-resource/mcp; only root when pathname is '/'). getOAuthProtectedResourceMetadataUrl builds the same URL — feed it the same URL object. Avoid a trailing slash on resourceServerUrl: the PRM `resource` becomes 'https://h/mcp/', the client then sends resource=https://h/mcp/ and the token aud must match; checkResourceAllowed tolerates the slash for prefix matching but exact-string verifiers do not. Client discovery tries the path-aware URL first and falls back to the root well-known on any 4xx.
- Resource URL must match what clients dial: the client's selectResourceURL throws 'Protected resource ... does not match expected' when the PRM `resource` origin differs from the server URL origin (or the path is not a prefix). Since the SDK computes metadata once from configured URLs, serve a single canonical public URL (env MCP_PUBLIC_URL) rather than deriving per request, or clients on 192.168.79.x vs 192.168.78.x will fail discovery; alternatively build/mount the metadata router per host or implement validateResourceURL on the client.
- mcpAuthRouter must be mounted at the application root (app.use(router)) because it uses absolute pathnames from the metadata; a path prefix in baseUrl/issuerUrl is discarded by `new URL('/authorize', base)`, so the endpoints are always <origin>/authorize, /token, /register, /revoke. mcpAuthRouter also always mounts /.well-known/oauth-authorization-server and the PRM route.
- Embedded AS limitations: /token supports only authorization_code and refresh_token (client_credentials -> 400 unsupported_grant_type); client authentication is read from the form body only (client_secret_post / none) — HTTP Basic is ignored (metadata correctly advertises ['client_secret_post','none'], and the SDK client picks post accordingly, but third-party clients that insist on Basic will fail with invalid_request/invalid_client); PKCE S256 is mandatory (code_challenge_method must be literally 'S256'); redirect_uri must be registered (exact, or loopback host with any port; 'localhost' and '127.0.0.1' do not cross-match); if redirect_uri is omitted it is only inferred when the client has exactly one registered URI.
- Rate limiting: /authorize 100/15min, /token 50/15min, /revoke 50/15min, /register 20/h via express-rate-limit v8 (in-memory, per IP). Behind a reverse proxy set app.set('trust proxy', <hop count>) — express-rate-limit v8 throws ERR_ERL_PERMISSIVE_TRUST_PROXY on `trust proxy: true`. Disable per endpoint with tokenOptions/authorizationOptions/revocationOptions/clientRegistrationOptions: { rateLimit: false }.
- DCR defaults: client_id = randomUUID, client_secret = 64 hex chars unless token_endpoint_auth_method === 'none', client_secret_expires_at = issued + 30 days (clientSecretExpirySeconds: 0 disables expiry); authenticateClient rejects expired secrets; clientIdGeneration:false lets your store assign IDs. The /register response is 201 with the full client record (secret included).
- Stateful sessions: keep one StreamableHTTPServerTransport (+ one McpServer) per session, register it in onsessioninitialized (fires inside handleRequest before the response is written), remove in onsessionclosed/onclose. The response header is lowercase 'mcp-session-id'. Missing header on non-initialize -> 400 (-32000); unknown -> 404 (-32001, the client transport treats this as session expiry); a second initialize on an initialized transport -> 400; DELETE -> onsessionclosed then transport.close() -> onclose. Session IDs are NOT bound to tokens — middleware re-verifies the bearer on every request; bind sessionId <-> clientId/sub yourself if you need to stop token swapping mid-session.
- Stateless mode: sessionIdGenerator: undefined; a transport instance may serve exactly one request (second handleRequest throws 'Stateless transport cannot be reused across requests'); create transport + McpServer per POST, close both on res 'close', and reply 405 to GET/DELETE.
- Accept/Content-Type strictness: POST needs Accept containing BOTH application/json and text/event-stream (else 406) and Content-Type application/json (parsed media type; else 415); GET needs Accept: text/event-stream (else 406). curl tests must send these headers or you will chase phantom auth bugs.
- Protocol version header: mcp-protocol-version is optional; if present it must be one of ['2025-11-25','2025-06-18','2025-03-26','2024-11-05','2024-10-07'] or the server returns 400. The SDK client sends it automatically after initialize. Discovery GETs from the client include 'MCP-Protocol-Version: 2025-11-25' and retry without custom headers on CORS TypeErrors.
- enableJsonResponse:true makes POST replies application/json (single object or batch array) instead of SSE; the GET stream stays SSE. SSE keep-alive comments are sent every 15 s (keepAliveMs; <1 disables); retryInterval sets the SSE retry field; eventStore enables Last-Event-ID resumability (priming events only for clients >= 2025-11-25).
- extra.authInfo only exists for messages that arrived through handleRequest with req.auth (Node wrapper) or options.authInfo (web-standard). Put the bearer middleware on POST, GET and DELETE; tools see the AuthInfo of the POST that carried their JSON-RPC request; extra.requestInfo.headers (lowercase keys) and extra.sessionId are also available.
- CORS: the SDK's metadata/token/register/revoke routers include cors() for any origin, but /mcp has none. For browser clients add cors({ exposedHeaders: ['Mcp-Session-Id','mcp-protocol-version'], allowedHeaders: ['Content-Type','Authorization','mcp-session-id','mcp-protocol-version','Last-Event-ID'] }).
- ProxyOAuthServerProvider: skipLocalPkceValidation is hard-set to true and challengeForAuthorizationCode returns '' — the upstream must enforce PKCE; getClient must return redirect_uris because /authorize validates them locally before redirecting; the upstream AS redirects the browser straight to the MCP client's redirect_uri (the proxy is not in the callback path), so those URIs must be registered upstream too; if getClient returns a client_secret, authenticateClient forces the MCP client to present that same secret in the /token body (so it is not a 'hide the upstream secret' pattern — subclass and inject the secret in exchangeAuthorizationCode/exchangeRefreshToken instead); upstream non-2xx surfaces as ServerError 'Token exchange failed: <status>' (HTTP 500 from /token) without the upstream error body; DCR passthrough only if registrationUrl; revocation only if revocationUrl; `resource` is forwarded to upstream authorize/token.
- External AS metadata typing: discoverAuthorizationServerMetadata returns OAuthMetadata | OpenIdProviderDiscoveryMetadata; the OIDC fallback is parsed with a STRIP schema that drops revocation_endpoint/introspection_endpoint. When you need those (or want to pass the doc to mcpAuthMetadataRouter which expects OAuthMetadata), fetch the discovery JSON yourself and OAuthMetadataSchema.parse it (loose, keeps everything). Keycloak's RFC 8414 document lives under the realm path, which the SDK's path-insertion probe (/.well-known/oauth-authorization-server/realms/x) does not find; its /realms/x/.well-known/openid-configuration is found on the third attempt.
- Client auth() specifics: `resource` is only sent when PRM was found; scope precedence = WWW-Authenticate scope > PRM scopes_supported > clientMetadata.scope (used for BOTH DCR and authorize); DCR only happens when clientInformation() is undefined AND saveClientInformation exists (else Error 'OAuth client information must be saveable for dynamic registration'); finishAuth/exchange requires existing clientInformation ('Existing OAuth client information is required when exchanging an authorization code') so persist it across the redirect; a scope containing offline_access adds prompt=consent; CIMD (SEP-991) client_id = provider.clientMetadataUrl is used only if AS metadata has client_id_metadata_document_supported:true and the URL is https with a non-root path.
- Client transport 401 handling happens only on POST; the GET SSE 401 path calls auth() without reading WWW-Authenticate. After auth succeeds a second consecutive 401 throws StreamableHTTPError(401,'Server returned 401 after successful authentication') (circuit breaker), and a 403 with error="insufficient_scope" triggers exactly one upscoping re-auth. Without authProvider, 401 is a StreamableHTTPError with code 401 (not UnauthorizedError). requestInit.headers override the automatic Authorization/session headers.
- After catching UnauthorizedError and calling transport.finishAuth(code), reconnect with a NEW StreamableHTTPClientTransport (start() throws 'already started' on reuse); Client.connect can be called again on the same Client instance (the SDK example does exactly this).
- Client credentials work only against an AS that implements the grant (Keycloak etc.), never against the SDK's embedded /token; ClientCredentialsProvider tokens are in-memory only and there is no refresh token — expiry is handled by re-running the grant on the next 401. private_key_jwt needs globalThis.crypto (Node >= 19 or polyfill).
- verifyAccessToken on an OAuthServerProvider is what requireBearerAuth uses when you pass verifier: provider — one object serves both roles. For separate AS/RS processes (SDK examples), the RS calls the AS's hand-rolled /introspect endpoint; the SDK ships no introspection server helper.
- registerTool inputSchema accepts a zod raw shape ({ a: z.number() }) or a zod object schema; the SDK imports 'zod/v4' internally and zod 4.5.1 is installed. Tool callbacks with no inputSchema are called as (extra) => ..., with a schema as (args, extra) => ...; return { content:[...], structuredContent?, isError? }.
- express.Router paths for the PRM are registered with router.use(path) so trailing-slash variants also match; but the `resource` string inside the document is exact — keep resourceServerUrl canonical (scheme, host, port, path, no fragment, no trailing slash).

## Client side

- Root import is broken in this build: package.json exports '.' -> ./dist/esm/index.js but dist/esm/index.{js,d.ts} do not exist. Always import subpaths: '@modelcontextprotocol/sdk/client/auth.js', '.../client/streamableHttp.js', '.../client/auth-extensions.js', '.../client/middleware.js', '.../client/index.js', '.../shared/auth.js', '.../shared/auth-utils.js', '.../server/auth/router.js', '.../server/auth/middleware/bearerAuth.js', '.../server/auth/providers/proxyProvider.js', '.../server/auth/errors.js', '.../server/streamableHttp.js', '.../server/express.js', '.../types.js'. Keep the .js suffix (ESM + typesVersions map).
- Error class on 401 depends on whether an authProvider is configured: WITH provider and interactive flow -> UnauthorizedError (message 'Unauthorized') from client.connect(); WITHOUT provider -> StreamableHTTPError with .code === 401 and message 'Streamable HTTP error: Error POSTing to endpoint: <body>'. The d.ts comment claiming UnauthorizedError is thrown when no provider is present is only true for the GET SSE path (_authThenStart), which is fire-and-forget and reports via transport.onerror.
- After a failed connect() the Client calls close() on the transport (AbortController aborted, _abortController stays set) — you MUST create a NEW StreamableHTTPClientTransport for the retry; calling start()/connect() on the old one throws 'StreamableHTTPClientTransport already started!'. The SAME Client instance can be reused (Protocol._onclose clears _transport). Call finishAuth(code) on the OLD transport (it remembers resource_metadata/scope from the 401) or on the new one (works too because auth() re-discovers or uses provider.discoveryState()).
- finishAuth(code) requires provider.clientInformation() to be non-undefined and provider.codeVerifier() to return the verifier saved by saveCodeVerifier — auth() throws 'Existing OAuth client information is required when exchanging an authorization code' otherwise. In a CLI both live in the same process, but if your CLI exits between redirect and callback you must persist client info + verifier (+ discovery state, + state param) to disk.
- client_credentials detection: auth() switches to non-interactive purely on `provider.redirectUrl` being falsy, and fetchToken() uses `provider.prepareTokenRequest(provider.clientMetadata.scope)` — note the scope passed is clientMetadata.scope, NOT the SEP-835 resolved scope (WWW-Authenticate/PRM scopes are ignored for non-interactive grants unless your prepareTokenRequest ignores its argument and picks its own). clientMetadata.grant_types is never read by the client runtime. The built-in providers keep tokens only in memory and never refresh proactively; a 401 triggers a new client_credentials grant (once — a second 401 after successful auth throws StreamableHTTPError 401).
- The SDK's own AS (mcpAuthRouter/tokenHandler) supports only grant_type authorization_code and refresh_token; 'client_credentials' returns 400 unsupported_grant_type (source comment: 'Additional auth methods will not be added on the server side of the SDK'). For M2M you need an external AS or your own /token route (you can still reuse authenticateClient + your provider.verifyAccessToken).
- Embedded AS client authentication is client_secret_post ONLY (authenticateClient reads client_id/client_secret from the form body; no HTTP Basic parsing). createOAuthMetadata advertises token_endpoint_auth_methods_supported ['client_secret_post','none'] so SDK clients pick post automatically; third-party clients that force Basic will get invalid_client.
- issuerUrl must be https unless hostname is exactly 'localhost' or '127.0.0.1' — http://192.168.78.x:3000 (LAN testing) throws 'Issuer URL must be HTTPS' from mcpAuthRouter AND mcpAuthMetadataRouter (it validates oauthMetadata.issuer too). Set MCP_DANGEROUSLY_ALLOW_INSECURE_ISSUER_URL=1 in dev. No query string or fragment allowed on the issuer.
- createMcpExpressApp() defaults to host '127.0.0.1' and installs localhost-only Host-header validation; when binding 0.0.0.0 for LAN clients pass { host: '0.0.0.0', allowedHosts: ['192.168.78.10','mcp.lan',...] } (hostnames without ports) or requests from other machines get rejected by hostHeaderValidation. It already applies express.json(); do not add a second body parser that changes req.body shape. Express 5.2.1 is the SDK's dependency (router.use with path strings, async handlers propagate rejections to the error handler; path-to-regexp v8 syntax — no '*' wildcards).
- requireBearerAuth REQUIRES AuthInfo.expiresAt to be a finite number (seconds since epoch) and rejects if missing ('Token has no expiration time') or past; opaque never-expiring API keys must synthesize an expiresAt. Throw InvalidTokenError (401 + WWW-Authenticate) or InsufficientScopeError (403) from verifyAccessToken; a plain Error becomes 500 with no WWW-Authenticate, so the SDK client will NOT start OAuth discovery.
- WWW-Authenticate parsing on the client: header must begin 'Bearer' + space + something; values matched by regex `field=("…"|unquoted)`; only resource_metadata, scope and error are read. The SDK server emits `Bearer error="invalid_token", error_description="…", scope="…", resource_metadata="…"`. If your own 401 omits resource_metadata the client falls back to path-aware well-known discovery on the MCP origin; if that 404s it treats the MCP origin itself as the AS (legacy) and tries /.well-known/oauth-authorization-server + openid-configuration there.
- PRM path rules: client requests `/.well-known/oauth-protected-resource<serverPath without trailing slash>` first (with the server URL's query string appended), then root `/.well-known/oauth-protected-resource` on any 4xx. Server mcpAuthMetadataRouter serves it at `/.well-known/oauth-protected-resource<resourceServerUrl.pathname>` (root if pathname '/'). A resourceServerUrl with a trailing slash ('/mcp/') produces a route with the trailing slash; express matches both, but the PRM `resource` value will then be 'http://h/mcp/'. selectResourceURL passes only if the connect URL's path is a sub-path of PRM.resource's path (with trailing slashes normalized) on the same origin, else throws 'Protected resource X does not match expected Y (or origin)'. Keep resourceServerUrl, the URL clients connect to, and the `aud` you validate identical (scheme+host+port+path, no fragment).
- Resource indicator (RFC 8707): the client only sends `resource=` when PRM was found (or validateResourceURL returns a URL); it uses PRM.resource (not the connect URL). Keycloak/Auth0 must be configured to accept that audience or drop it via provider.validateResourceURL = async () => undefined.
- AS discovery order (buildDiscoveryUrls): issuer without path -> /.well-known/oauth-authorization-server, /.well-known/openid-configuration; issuer with path /p -> /.well-known/oauth-authorization-server/p, /.well-known/openid-configuration/p, /p/.well-known/openid-configuration. Keycloak realms resolve on the third try (two 404s first). All 4xx are skipped, 5xx throws. OIDC documents are validated with OpenIdProviderDiscoveryMetadataSchema (needs jwks_uri, subject_types_supported, id_token_signing_alg_values_supported) — a hand-rolled minimal openid-configuration missing those fields fails zod and discovery returns undefined, after which the SDK guesses `${as}/authorize`, `${as}/token`, `${as}/register`.
- Discovery requests carry `MCP-Protocol-Version: 2025-11-25` (LATEST) and `Accept: application/json`; on a CORS TypeError they retry without headers. MCP requests carry `mcp-protocol-version` only AFTER initialize (negotiated version); the server rejects the header only if its value is not in SUPPORTED_PROTOCOL_VERSIONS (400). Client.connect fails with 'Server's protocol version is not supported' if the server negotiates something outside ['2025-11-25','2025-06-18','2025-03-26','2024-11-05','2024-10-07'].
- Header precedence in the client transport: provider Bearer -> mcp-session-id -> mcp-protocol-version -> then requestInit.headers spread last, so a requestInit Authorization header silently overrides the OAuth provider's token. Also requestInit is passed into auth() via createFetchWithInit, so those extra headers are sent to the PRM/AS/token endpoints too (beware leaking API keys to a third-party AS).
- Scope selection (SEP-835) for the code flow: options.scope (from WWW-Authenticate) > PRM.scopes_supported.join(' ') > clientMetadata.scope; the same resolved scope is used for DCR and the authorize request. If PRM advertises scopes_supported the client will request ALL of them. `offline_access` in scope adds prompt=consent.
- DCR requires provider.saveClientInformation, otherwise auth() throws 'OAuth client information must be saveable for dynamic registration'. If AS metadata exists but lacks registration_endpoint -> 'Incompatible auth server: does not support dynamic client registration'. Registered client info (incl. token_endpoint_auth_method returned by the AS) drives selectClientAuthMethod; secrets from the SDK's own /register expire after 30 days by default (clientSecretExpirySeconds; 0 = never) and an expired secret yields invalid_client -> client invalidateCredentials('all') -> re-registration.
- Refresh handling: refreshAuthorization preserves the old refresh_token when the AS does not rotate it. On refresh failure with ServerError or a non-OAuthError (network) the SDK silently falls through to a NEW authorization redirect; with InvalidGrantError it invalidates tokens and retries once (ending in a redirect); with any other OAuthError it rethrows out of connect(). The transport never checks expires_in — expiry is only discovered via a 401.
- 403 handling: only when WWW-Authenticate contains error="insufficient_scope" and an authProvider exists; the SDK re-runs auth() with the header's scope (upscoping) once per distinct header value; note this path calls auth() with fetchFn: this._fetch (NOT fetchWithInit), so requestInit headers are not applied during that discovery.
- Session semantics: stateful server (sessionIdGenerator) returns mcp-session-id on the initialize response; the client stores it and sends it on every request; a server restart makes the id unknown -> 404 'Session not found' -> the client does NOT auto-reinitialize; catch it and rebuild transport+connect. Passing sessionId in the client options makes Client.connect() SKIP initialize entirely (reconnect semantics), so only pass it for a session you know is alive. Server side, protect GET/DELETE with the same bearer middleware and, if you want per-user isolation, bind the session id to req.auth.clientId/sub yourself — the SDK does not.
- POST requests must send Accept containing both application/json and text/event-stream (else 406) and Content-Type application/json (else 415); the SDK client does this. GET stream returns 405 when unsupported and the client treats that as fine.
- Loopback redirect URIs: the SDK AS (redirectUriMatches) relaxes only the PORT for localhost/127.0.0.1/[::1] and requires identical hostname/scheme/path/query — register 'http://127.0.0.1:PORT/callback' and use exactly 127.0.0.1 (not localhost) at runtime, or vice versa. The CLI callback listener should bind 127.0.0.1; it is the user's browser on the same machine that hits it, so this does not conflict with the LAN-testing rule for the MCP server itself.
- OAuthClientMetadata.redirect_uris is REQUIRED by the zod schema (array; may be empty for M2M). SafeUrlSchema (z.url()) rejects non-URL strings; logo_uri/tos_uri accept ''.
- private_key_jwt helpers dynamically import 'jose' and need globalThis.crypto (Node >= 19 or polyfill). Audience defaults to metadata.issuer, then the token URL — Keycloak expects the token endpoint URL or issuer depending on version; pass audience explicitly via createPrivateKeyJwtAuth if needed.
- withOAuth middleware is redundant for StreamableHTTPClientTransport (built-in handling) and its default serverUrl is the request ORIGIN only (path dropped) — pass baseUrl explicitly (the MCP URL) or PRM discovery will hit /.well-known/oauth-protected-resource at root only. withLogging default logger writes to console — never with stdio transports.
- ProxyOAuthServerProvider: challengeForAuthorizationCode returns '' and skipLocalPkceValidation=true, so the upstream AS MUST enforce PKCE; upstream calls always use client_secret_post form auth and never Basic; registerClient proxies the raw DCR body to registrationUrl and returns upstream's response — but authorizationHandler/authenticateClient still call YOUR getClient, so you must persist what upstream returned (client_id/secret/redirect_uris) or later /authorize and /token fail with invalid_client. Upstream error bodies are not parsed: failures become ServerError('Token exchange failed: <status>') -> client sees ServerError -> in refresh path this silently falls back to a new redirect.
- express-rate-limit is enabled by default on /authorize (100/15min), /token (50/15min), /register (20/h), /revoke (50/15min) keyed by IP — automated test suites hammering one IP will get 429 too_many_requests; pass `{ rateLimit: false }` in tokenOptions/authorizationOptions/clientRegistrationOptions/revocationOptions during tests. Behind a proxy set app.set('trust proxy', ...) or all clients share one key.
- tokenHandler/authorizationHandler/registration use cors() with any origin; the /mcp routes you write do not — add cors yourself if browser clients connect, exposing 'mcp-session-id' and 'mcp-protocol-version' headers.
- Error subclass identity matters for auth() retries: the client compares `error instanceof InvalidClientError` etc. imported from '@modelcontextprotocol/sdk/server/auth/errors.js' — if you have two copies of the SDK in node_modules (peer/dedupe issue) instanceof checks fail and the automatic re-registration/refresh recovery silently degrades to a thrown error.

## How the examples apply these facts

| Fact | Where it is handled |
|---|---|
| `MCP_DANGEROUSLY_ALLOW_INSECURE_ISSUER_URL` is read once at module load | `src/shared/env.ts` is the first import of every entrypoint and sets it; `tests/conventions.test.ts` enforces the order |
| `createMcpExpressApp()` binds 127.0.0.1 and only accepts localhost `Host` headers | `src/shared/http.ts` uses plain Express, binds `0.0.0.0`, validates `Host` against `PUBLIC_HOST` + loopback (+ `MCP_ALLOWED_HOSTS`) |
| `req.body` must be handed to `transport.handleRequest` when a JSON body parser runs first | `mountMcp()` in `src/shared/http.ts` |
| `AuthInfo.expiresAt` (seconds) is mandatory; only `InvalidTokenError` / `InsufficientScopeError` produce a `WWW-Authenticate` header; the error message is interpolated unescaped into that header | every verifier: `src/shared/jwt.ts`, the API-key verifier (01), the introspection verifier (07), the certificate middleware (08) — static messages only |
| PRM lives at `/.well-known/oauth-protected-resource<path>`; `resource` must equal the URL clients dial, no trailing slash | `src/shared/prm.ts`, one canonical `publicUrl(port)` everywhere |
| `mcpAuthMetadataRouter` also mirrors the AS document on the resource-server origin | pure resource servers (04, 05, 07, 09, 10) use `metadataHandler` at the PRM path only; 03 and 06 use `mcpAuthRouter` because there the MCP origin *is* the AS |
